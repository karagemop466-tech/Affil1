S-04

Apply for the Creators API — knowing it is gated behind 10 qualifying sales

an application, plus qualifying sales on most accounts

Why

Program Policies §2(b) permits price and availability only where Amazon serves the data or it arrives through the Creators API or PA API. Amazon's own documentation now records PA-API 5 as deprecated and returning 403 AccessDeniedException, and lists the Creators API prerequisites as Associates enrolment plus at least 10 qualifying sales within the past 30 days. The policy text still names both APIs, so following the policy alone would aim at a route that no longer answers.

Risk
Low, but the sequence is not negotiable: live prices arrive after the site proves it can sell, not before. A separate clause also requires a comparison-format price display to show the lowest used price as well as the lowest new, which is a second reason the comparison table stays blank.

S-19

Request sub-tag Associate IDs so attribution comes from Amazon's own report

a support request, then a small change to how each page builds its outbound links

Why

Program Policies §2(b) allows Amazon to issue additional sub-tag Associate IDs on request so an Associate can “monitor and optimize the performance” of different links. A sub-tag per page turns “which guide earns?” into a question Amazon's own report answers, which is far stronger evidence than anything a first-party counter can produce. The same clause forbids tying a sub-tag to an identified visitor, which this site does not do.

Risk
Low. Sub-tags are subject to Amazon's approval, so the answer may be no, and nothing else on the site depends on it. It complements S-01 rather than replacing it: S-01 proves a click is credited at all, sub-tags say which page earned it.
Depends on
S-01
Recommendation
Request it in the same dashboard session as S-01

S-20

Schedule the link re-check so drift is reported rather than discovered

an hour to wire the existing tool into a scheduled run and publish its output

Why

Every product fact on this site rests on a supplied link resolving to the same listing it did on 2026-11-20. P-04 already showed that the same link can return a product page on one attempt and Amazon's continuity page on another, on the same date. The repository already has the tool for this (tools/verify_links.py); what is missing is a schedule and a place for the result.

Risk
Medium, and worth stating plainly: an unattended re-check can hit the same interstitial P-04 did, and a false alarm is worse than no alarm. Any automated check must report the outcome and let a human adjudicate. It must never overwrite a verified record on its own.

The one recommendation to read twice

Everything else on this page adds something. S-07 says stop: do not commission more guides until either a real test or real search data exists. More synthetic prose makes the publication bigger, not better, and it raises the chance the whole site is treated as one undifferentiated block.

The nine guides that exist are defensible because they claim little. That is a narrow advantage, and it survives by not being diluted.

Design brief for the next iteration

Design a warm, magazine-style kitchen shortlist. Lead with one cooking decision, then show the three appliance formats using consistent cards. Pair every card with a specific thing to measure or check. Reuse a cover, a shortlist, a seasonal story and a single RSS invitation. Use only labeled editorial illustrations and attributable bylines. Do not use “best”, fake reviews, discount badges or star ratings without substantiation.

Cadence: Review evidence every week; plan one question-shaped guide per fortnight once collection and Search Console are live. Publish only after the fact, image and disclosure checks pass, then verify its canonical URL in both sitemap and RSS. Review the prior guide on the same date window each cycle.
