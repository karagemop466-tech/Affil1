Measurement

Five events,
and a collector that is off

The client is written, the collector is written and tested, and neither is switched on. That is the state, and this page explains why it is the right one until an endpoint is deployed.

Beacon disabled by default · no cookies · honouring GPC and DNT · no third-party requests

The brief asked for a privacy-preserving outbound-click counter and a self-hosted analytics endpoint, and for click and conversion measurement to exist before more writing. All three exist in this repository. The first two are live in code; the third is not live on the internet, because GitHub Pages serves static files and nothing else.

What that means in plain terms: the site currently knows nothing about its readers. It has no sessions, no clicks, no conversion rate and no revenue. Those numbers are absent, not estimated.

What each event answers

EventFires whenWhat it is for, and what it is not
page_viewEvery page renderCounts a visit. Stores the path with the query string stripped, so nothing typed into a URL is kept.
outbound_product_clickAny click on an Amazon linkRecords which ASIN was clicked and the page it was clicked from. This is the number that matters for this site, and it is still not a sale.
guide_read_75A reader reaches 75% of a guide&#x27;s heightSeparates readers who arrive to read from those who bounce. Crude: it measures scroll, not comprehension.
compare_viewThe comparison page rendersTests whether readers want side-by-side data more than prose. That answer decides what the next page should be.
flag_page_viewThe review queue is openedShows whether the verification work is actually consulted, or whether it is furniture.

What is collected, precisely

Four fields per event: the event name, the page path with the query string removed, the product ASIN for a click, and the date. That is the complete list. The client sets no cookie, writes nothing to local storage, and sends nothing if Global Privacy Control or Do Not Track is present.

The collector in analytics/collect.py does not read the client address, does not read the user agent, does not read the referer header, and rejects any field not on that list. It stores an integer count per day, per event, per path. There is no per-visitor record to retain, breach or join to anything else.

Why conversions are not an event

A browser cannot see what happens after a click leaves for Amazon. Any site claiming to measure conversions from its own beacon is either guessing or describing Amazon's report. Reported orders, when they exist, will come from the Associates report and will be entered in the campaign ledger with a date and a provenance note.

What has to happen before it goes live

  1. Deploy the collector somewhere that can run a process. A container, a small VPS or a serverless function all work. GitHub Pages cannot host it.
  2. Set one line. window.CC_ANALYTICS_ENDPOINT in the page shell in tools/layout.py, then rebuild. That is the entire integration.
  3. Publish the privacy notice. It exists at /privacy.html and describes exactly these four fields.
  4. Send one test event and read it back. The collector exposes an aggregate summary endpoint so the check is a number, not a hope.

The order that actually works

Tag the links, confirm one click in the Associates report, then measure. This site's links are now tagged and enforced by the build; the confirmation inside the account is still outstanding and is recorded as FLG-002. Measuring traffic before that confirmation would produce a chart of people arriving at a door that may not open.

What the campaign ledger holds

Nothing. It has a defined schema and a provenance rule, and no rows, because no authorised report has been supplied. See the empty ledger.
